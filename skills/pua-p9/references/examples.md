# P9 delivery lead｜可复现案例

## 使用说明

- **何时使用：** 交付包含多个可独立拥有的制品、明确依赖和最终集成验收，且协调/委派已获允许。
- **准备/输入：** 共享目标、工作单元、互斥所有权、输入输出契约、依赖图、集成环境和共同证据门。
- **执行方式：** 只并行独立部分，按实际制品验收子结果，解决接口冲突后运行端到端路径。
- **验收/边界：** 每个制品有唯一所有者且集成通过；不得靠代理数量、状态摘要、多数投票或虚构层级证明进展。
- **失败处理：** 子结果冲突时回到共享契约和真实制品，重新跑共同验收；无法集成的依赖必须标出唯一负责人或决定。

## 正向案例

### 协调前后端完成可验收交付

- **用户请求：** “把账号删除功能拆成前端、API 和审计三块，协调执行并确保集成可验收。”
- **准备信息/输入：** 用户目标、API 契约、数据保留规则、允许的目录、集成环境、测试命令与明确的委派授权；生产发布不在范围内。
- **处理：** 先画依赖顺序；为 UI、API、审计分别定义互斥文件所有权、输入输出和完成证据；只并行独立部分；收回结果后核对接口、错误码与审计字段，再运行端到端删除/取消/失败路径。
- **预期输出：** 三个可追踪制品、一个集成结果与未决依赖清单；代理数量不作为进展。
- **验收证据：** 每块有唯一所有者和实际差异；共享契约一致；端到端测试覆盖确认、取消、权限拒绝和审计记录；集成分支无未解释冲突。

## 边界案例

### 没有委派授权且文件高度重叠

- **用户请求：** “进入 P9 模式，多开几个 Agent 同时改这个单文件脚本，越快越好。”
- **准备信息/输入：** 环境没有委派授权；所有工作都集中在同一个脚本和同一套状态机。
- **边界判断/处理：** 不擅自创建执行单元；说明并行会造成重叠所有权和合并风险；直接顺序处理，或在用户明确授权后仅把只读调查与实现分开。
- **预期输出：** 一个清楚的执行边界，而不是人为制造并行活动。
- **验收证据：** 没有未授权委派；目标脚本只有一个修改者；如提出后续拆分，接口与独立性依据写明。

## 失败与恢复

### 两个子结果对同一状态定义冲突

- **失败场景/用户请求：** “前端说删除成功用 200，API 结果写 202，选多数意见赶紧合并。”
- **准备信息/输入：** 共享契约规定异步删除；前端假设即时完成；审计消费者依赖 pending 状态。
- **处理与恢复：** 停止多数投票；回到契约与真实行为；运行 API 集成测试并检查审计消费者；统一为有证据支持的异步状态，更新前端状态机与共同测试。
- **预期输出：** 一个一致的接口和用户状态流；冲突原因与采用依据可追溯。
- **验收证据：** UI、API、审计对 pending/completed/failed 含义一致；集成测试通过；被放弃方案及原因写入交付，而不是静默覆盖。
